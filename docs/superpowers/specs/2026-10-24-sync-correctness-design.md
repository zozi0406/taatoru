# Synchronization correctness and reference parity

Date: 24 October 2026. Status: proposed design for the requested repair plan; no implementation authorized by this document alone.

## Intent, scope, and approach

Repair every synchronization finding from the 24 October audit, including the adjacent answer-commit race. Match the useful reliability protections of both local reference applications, then address their known shared weaknesses instead of treating their behavior as a correctness specification. Completion means demonstrated invariants and a reference comparison with no unexplained regression. It cannot mean a promise that no unknown defect exists.

Recommended approach: preserve Expo, TypeScript, SQLite, the resource repositories, transactional session completion, and full-refresh transactions. Introduce one synchronization coordinator, persisted ownership/account fencing, and explicit pending-operation reconciliation. This is a connected reliability change, delivered in individually tested commits.

Alternatives considered: isolated fixes at each entry point leave cross-runtime races and inconsistent pending-state rules; replacing the sync/database stack adds migration risk without removing WaniKani's API constraints. Neither is recommended. These are planning recommendations, not choices already approved by the user.

Only Taatoru changes. Tsurukame and Smouldering Durtles remain read-only. Preserve all existing visual and study-UX changes. The study-UX design owns question presentation, overrides, settings, picker persistence, and session resume; this plan owns durable correctness, upload delivery, and tests of their shared boundaries. Re-read that work before implementation and integrate its commit guard rather than introducing another one. A small, additive Taatoru database migration is necessary to survive process death and coordinate different connections; the study-UX document's no-migration boundary remains applicable to its own work.

## Required invariants

1. Each accepted local completion and its session snapshot are persisted atomically with an immutable operation identity. A failed commit does not advance the screen.
2. Pending completion cannot become available again or lose its projected state because of quick sync, full refresh, pagination, or an unrelated resource failure.
3. Pending notes and synonyms remain the effective local values until acknowledged, superseded through an explicit policy, or explicitly discarded.
4. One account has at most one active sync owner across engines/connections. Stale owners cannot commit resource data, acknowledge operations, publish account state, or schedule account notifications.
5. Logout/account replacement invalidates old work before clearing data or replacing credentials. Same-account token rotation preserves pending operations while invalidating old request credentials.
6. Committed work triggers an online delivery attempt; bounded retries and quota-reset continuation drain runnable work without another connectivity transition. Background execution is opportunistic, not a timing guarantee.
7. No resource cursor advances past a conservative safe watermark; rows and cursor commit together. Empty results never clear a valid cursor. Replays cannot overwrite newer server data with older versions.
8. Hidden, locked, reset, and subscription transitions reach local eligibility rules and invalidate affected sessions/pending operations before unsafe uploads.
9. A transport failure, malformed success body, 422, or lost acknowledgement never silently erases unverified work. A poisoned item does not block unrelated eligible operations or downloads.
10. UI status distinguishes downloaded data, queued work, server-acknowledged work, superseded work, and work needing attention. Only zero pending work in every delivery state, including future retries, may be described as fully synchronized.

## Data and ownership boundaries

Keep existing cache tables and pending tables. Add schema version 2 through ordered migrations; do not rewrite version 1 or clear a user's database. Use a singleton control row for account identity, account epoch, credential revision, auth transition state, lease owner/fence/deadline, operation sequence, reset baseline/cursor, and request pacing/budget state. Preserve account/fence counters across logout. Store no credential or token fingerprint in SQLite.

Extend pending rows with stable operation identity, account epoch, operation revision, delivery state, retry time/count, lease claim, original assignment version/stage/availability, fixed wire timestamp, and the minimum projected state required to restore local views. Values required by only one queue stay on that queue. Allocate IDs using a database sequence inside the enqueue transaction, without a new random-ID dependency. States are `queued`, `in_flight`, `uncertain`, and `rejected`; acknowledged or superseded rows leave the pending table only in the same transaction that imports authoritative state and records a small content-free outcome. Superseded means the server state now takes precedence, not proof that this client's review was accepted.

Add a `sync_dispatches` table keyed by operation identity and revision, storing the immutable baseline, target, payload, fixed timestamp, and delivery state of every dispatched revision until it is settled. Updating the latest pending material row must never overwrite that evidence. A subject with an unresolved dispatch reconciles it before sending its newer revision; unrelated subjects can proceed. These are local durable payloads, not diagnostic logs.

Version-1 pending rows lack some provenance. Migrate their content unchanged; use existing cached/protobuf JSON when trustworthy and otherwise mark them for reconciliation, not blind submission or deletion. Never invent the original SRS stage or original assignment version. Test fresh install, populated migration, rollback, reopen, repeated startup, and two connections attempting migration. Recheck the schema version after obtaining the migration write lock.

Use a shared coordinator within a runtime and a SQLite ownership lease across connections. Proposed defaults: 120-second lease, renewal every 30 seconds, 30-second network request deadline, and monotonic owner fences. Do not hold a database transaction open over a network request. All cache replacement, pending acknowledgement, and account mutation use transactions that check account epoch, credential revision, and owner fence. Serialize/busy-retry lock acquisition; do not confuse another connection's SQLITE_BUSY with an empty queue.

Mark an operation `in_flight` before its request is dispatched. A dead owner's `in_flight` work becomes `uncertain`, never directly runnable. A lease timeout or AbortController cancellation is not proof that the server stopped processing. Fence late callbacks and reconcile before replay. If a suspended former worker resumes, it must validate ownership before every dispatch as well as every commit. Already-dispatched server effects cannot be retracted; they remain bound to the credential/account with which they were sent.

Authentication uses a fail-closed transition journal and versioned SecureStore slots. Reserve a globally increasing credential revision in SQLite, invalidate network ownership, and mark the transition before storing the candidate token at `taatoru.credential.<revision>`. Store only that slot name and transition ID in SQLite. Validate `/user` using the reserved transition; activate the slot pointer only if that exact transition is still current and the account-change policy allows the identity. Each auth transition writes a different SecureStore key: a suspended old login cannot overwrite the active token, even if its later SecureStore write finishes after another login. Old/unreferenced slots may be cleaned up; never reuse a revision or delete a currently active/pending slot. Read-only authentication requests use a transition reservation, not an invented active-account context.

Restart repairs interrupted transitions before uploads: read the journal's reserved slot, validate the candidate, and conditionally activate; if missing/invalid, leave existing cached reads available and require credential repair. A missing active slot also blocks uploads. Migrate the legacy single token slot through this protocol after validation, and remove the old slot only after activation. Logout first clears active/pending pointers and increments fences in SQLite, then removes their known SecureStore slots; a late orphan write stays unreachable. Explicit replacement of another account clears account-owned data under a new epoch; same-account credential replacement preserves its queue. Logout with pending work must offer a concrete upload/cancel/discard choice and must not claim successful upload when requests remain unresolved.

## Effective local state and downloads

Assignments remain a cache of server truth: stop deleting them on local completion. Available lesson/review queries exclude subjects with active pending progress. `subject_progress` remains the effective projection used by existing consumers; store the pending projected stage at enqueue and reapply it inside every assignment import/full replacement. Preserve recent mistakes. Rejected/uncertain subjects stay protected until reconciliation or an explicit user resolution. Launch/resume checks use the same eligibility seam, not independent SQL variations.

Keep server resource JSON/timestamps as server truth while effective note/synonym scalar fields incorporate the newest pending edit. Rebuild search synonyms from effective material after both subject and material imports: the current subject importer resets FTS synonyms even when the material endpoint returns no changes. Apply the same effective-state policy to subject details, answer checking, counts, forecasts, analytics, notifications, and full replacement. Do not fabricate exact offline review schedules from the existing approximate SRS stage projection; server-returned assignments determine actual due times.

Replace speculative ID-window pagination with actual `next_url` traversal for subjects and review statistics. Preserve the first page's collection watermark; never replace it with a later page's moving timestamp. Subsequent incremental requests replay a one-second overlap, preserving original timestamp strings and microsecond ordering. An empty page retains the previous persisted cursor. Upserts reject server versions older than their cached server version. Validate repeated URLs, sparse IDs, duplicates, page-size variation, partial failures, and updates to an already-read ID. A full refresh still commits its complete generation atomically, with pending overlays applied in that transaction. Targeted write receipts must not advance collection cursors.

Remove `hidden=false` and `unlocked=true` filters from synchronization reads; keep hidden/locked records in the cache and exclude them in user-facing queries. Keep subscription-content restrictions at read/use boundaries. Before uploading a batch, fetch/validate the user and new reset records, and refresh relevant assignment state. Detect confirmed resets, including same-level reset and reset followed by re-leveling, through `/resets`, not just a decrease in user level. Rebuild progress caches on a newly confirmed reset; revalidate outstanding operations and sessions against the reset time and new assignments. Unknown legacy provenance needs reconciliation. Preserve unrelated material edits and settings. If reset detection or preflight cannot complete, keep local study available where safe but do not upload unvalidated old progress.

Offline clients cannot detect a reset or another device's changes until they reconnect. An external change can also occur after preflight; response reconciliation remains required. These are API/distributed-system limits, not cases to conceal with optimistic success.

## Delivery, retries, and server outcomes

The coordinator receives wakeups after durable enqueue, app startup/foreground resume, stable reconnection, manual refresh, credential repair, and background-task launch. Coalesce wakeups. A full-refresh request arriving during a quick run must remain scheduled; an enqueue during a run must cause another drain check. Use a bounded background slice of 20 seconds, persist continuation metadata, and stop dispatching with sufficient time to clean up. The next foreground/background opportunity resumes; no promise of an exact background execution time.

Pace all requests, including reads, login/preflight, reconciliation, and pagination, through one scheduler: at most one in flight per owner, at least 1,100 ms between dispatches, plus the stricter valid server `RateLimit-*` budget and `Retry-After` deadline. Persist exhausted-budget/deadline state so a new engine cannot reset it. Reserve enough capacity to finish a safe operation/reconciliation step; dynamic actual request cost replaces speculative fixed page estimates. Retries use 2, 4, 8, 16, 32, then 60 seconds plus up to 20% jitter, with injected clock/randomness in tests. Honor server delays even when longer. Do not sleep a background worker through a long quota wait.

Network errors/5xx cause backoff; uncertain writes reconcile first. 401 pauses uploads for credential repair. Hibernation/permission 403 pauses appropriately and exposes the existing account notice. 429 persists the deadline and schedules foreground continuation. Definite per-item validation errors become `rejected` with an actionable, redacted reason; unrelated work and reads continue. SQLite/ownership failures stop the current owner. No raw answer, note, synonym, account payload, or token enters diagnostics.

Return typed success resources from assignment start, review creation, and study-material upsert. Import write-returned assignment/statistics/material state and conditionally acknowledge the exact operation revision in one fenced transaction. An undecodable successful write is uncertain; a later failed notification refresh does not make an already-acknowledged write uncertain.

Persist the wire completion timestamp before first dispatch and reuse exactly the same payload on retry, including recent reviews. Validate it against the original due/unlock boundary and server-time offset; clock skew must not silently become a perfect review, a new timestamp on replay, or a discarded 422. A clock/boundary inconsistency requires refreshed authoritative data and a visible resolution if still invalid. Replaying an old operation must never turn it into a later review cycle.

Reconcile uncertain/rejected progress by fetching the specific assignment and its review statistic, checking reset generation and the original opportunity. Store original review-statistic counters when available. A newer `data_updated_at` alone is never grounds to discard progress. Classify outcomes with these explicit rules:

- A matching successful receipt acknowledges this operation.
- A confirmed reset affecting the subject and invalidating the opportunity on which completion was based, a replaced assignment identity/new resurrection, or a now-hidden subject supersedes the old opportunity with its explicit reason. When timing/provenance is missing, preserve it for attention instead of guessing.
- A lesson whose same assignment is already started is superseded as started remotely; an unchanged unstarted/unlocked assignment remains retryable. Subscription loss pauses its upload, not permanent supersession.
- A review with the same identity/reset/resurrection, SRS stage, due boundary, and counters remains the same opportunity even if unrelated resource metadata changed. It is retryable with its fixed valid payload after backoff.
- A review whose authoritative counters advanced and whose due boundary advanced or which is burned has consumed the original opportunity. Settle it as superseded/remote progress, without claiming this client's answer counts were accepted.
- A moved due time with unchanged counters can be a vacation/scheduling change, not proof of review completion. An unexplained stage change, missing counter baseline, failed lookup, or ambiguous identity remains preserved for attention. Refresh server time/eligibility before considering another send.

Do not query review history: that API is deprecated and returns no reviews. There is no documented server idempotency key; do not claim mathematical exactly-once delivery or infer that another device's advancement proves this client's answers were accepted.

For study-material creation, consume the created resource ID, look up existing material by subject after ambiguous creation or duplicate-create response, and update surviving newer pending revisions to that ID without changing their content. Retain the older dispatched revision in `sync_dispatches` through acknowledgement/reconciliation. If remote values match that dispatched payload, its desired state is satisfied; rebase the newer revision's original server baseline to those values and preserve the newer desired content. Do not mistake this client's earlier upload for a remote edit conflict. A definite 404 on update triggers lookup before choosing POST again. A failed lookup must not be interpreted as absence.

Concurrent remote edits use field-level comparison against the original cached server values and any unresolved dispatch: merge disjoint changes, retain original/dispatched/newest-local/remote versions when needed, and surface observed same-field conflicts rather than silently overwriting them. Synonym arrays count as a single field for conflict detection; do not invent a union policy that prevents intentional removal. This requires preserving the original edited-field baseline and immutable dispatch, not just the final edited payload. No documented server compare-and-set primitive protects material updates: another device may edit after this read and before this PUT, and an old uncertain PUT can finish after a newer revision. In those unavoidable windows server effects may overwrite a more recent edit despite local fencing; do not advertise general conflict-free multi-device notes. Include a controlled late-write fixture and record this shared API limitation in the comparison matrix.

## Session transitions and UI

Adopt one synchronous in-flight guard for all lesson/review transitions, including answer, Continue, override, presentation navigation, Finish, and Exit. Disable competing actions while persistence is pending; update the rendered snapshot only after commit. A rejected commit retains the prior answer/snapshot and offers retry. Account teardown and stale sessions invalidate callbacks. Reuse the study-UX implementation if it has already supplied this behavior. Include accepted meaning synonyms from effective local materials in the real lesson/review answer-checking path; pure checker support alone is insufficient.

Publish one account-scoped store from the coordinator and replace no-op invalidation with updates after local commits and downloads. Dashboard and subject/session consumers reload at the established focus/version boundary. Display separate pending, uncertain, rejected, retry-at, and superseded counts. Distinguish library refresh success from queue settlement; keep Finish usable after a durable offline completion, without implying remote success. User resolution cannot silently discard work or reapply a superseded review.

## Evidence and release contract

The repair plan must map every audit finding to a task and test. Tests use controlled API fixtures, deferred request barriers, fake timers, actual SQLite transactions, and two independent connections to one file. Cover process death before/after send and acknowledgement, late callbacks after lease expiry/logout, reset plus pending work, clock skew, token rotation, empty/partial pages, material edit-during-create, and queued UI transitions. Validate the actual Expo SQLite adapter on Android, not just the synchronous Node test adapter.

Before release: complete `npm run verify` under Node 22; build an Android debug app and exercise the fixture-backed fault scenarios on an emulator/device; manually check ordinary lessons/reviews, picker/cancel, restart/resume, rotation, dark theme, large text, long lists, offline completion/reconnect, and foreground/background contention. No real account mutations are required for this gate. Record commands/results and any unsupported device check. If iOS release is later proposed, require physical-device background/lifecycle verification before claiming parity there.

Do not ship a partial milestone as fully hardened. A checked comparison matrix must show Tsurukame's immediate delivery and transactional completion, Durtles' shared serialization/pacing/reconciliation, Taatoru's existing stronger full-refresh/conditional-acknowledgement behavior, and the shared reference weaknesses fixed here. Unknown review outcomes, non-atomic remote preflight/updates, and OS-controlled background timing remain explicitly stated limits. Preventing old reviews from becoming later-cycle attempts is a client dispatch/payload invariant together with documented server timestamp validation, not an assertion that preflight atomically fences a remote reset or another client's progress.
